# 温控算法与实测数据

← 返回 [README](../README.md)

本文说明转速是怎么算出来的，以及所有参数的整定依据。实现见 `Sources/FanControlCore/FanCurveEngine.swift`。

---

## 1. 本机实测数据（所有校准的依据）

下表是 **M4 Mac mini（Mac16,10，10 核，风扇 1000–4900 RPM）** 的实测结果。温度是**平滑后的核心平均温度**，括号里是平滑后的单核峰值：

| 场景 | 1000 RPM（最低） | 4900 RPM（满速） |
|---|---|---|
| **真空闲** | **~52°C**（峰值 ~62°C），稳定 | **~48°C**（峰值 ~60°C），稳定 |
| **10 线程满载** | **>87°C 且持续上升**（峰值 >103°C）<br>90 秒未收敛，被迫中止测试 | **~65°C**（峰值 ~79°C）<br>30 秒内收敛，非常稳定 |

三条结论：

1. **风扇在负载下的控温能力约 22°C（平均）/ 24°C（峰值）**——非常大，值得用。
2. **macOS 默认策略在满载时把风扇死守 1000 RPM**，压不住，温度会一路爬到 SoC 自己降频。
3. **真空闲是 52°C，不是 71°C。** 早期版本的曲线按 71°C 的空闲基线校准，那个 71°C 其实是"边编译边测"的污染数据。按 71°C 起步的曲线在日常使用时长期输出 0（等于没装这个软件），等温度冲过 87°C 又突然满速，体验是"要么不动要么狂转"。现在的控制点已按上表重新校准。

> 满载测试的第一阶段（满载 + 最低转速）因平滑峰值温度超过 103°C 被主动中止。这本身就是结论：macOS 默认风扇策略压不住 M4 mini 的持续满载。

Intel 曲线**未经实机验证**，仍按 Intel Mac 的传统温度量级（空闲 40–50°C、满载 90°C+）给出，没有做过上面这种四象限实测。

## 2. 控制周期

每 0.7 秒一个周期，依次做四件事。

### ① 取温度

枚举 SMC 全部键，挑出 CPU 核心簇传感器，算出两个量：

- **核心平均温度** → 喂给曲线和 PI 控制器
- **单核峰值温度** → 喂给高温保护

### ② 低通平滑

对两个量各做一阶 EMA，时间常数 8 秒。

这一步不能省：Apple 芯片的单核传感器噪声极大，实测同一秒内不同核心能差 20°C 以上，单核瞬时值在有负载时一秒内就能从 74°C 跳到 97°C。直接拿瞬时值查曲线，风扇会一直抖。

**所以曲线和 PI 的输入一律是平滑后的平均值，绝不是最高值。**

### ③ 决定目标比例

按模式分成开环和闭环两条路，详见下面第 3、4 节。

### ④ 升降速限速（滞回）

转速不会直接跳到目标值，而是限速逼近：**升速最快 30%/秒，降速最快 5%/秒**。

降速刻意比升速慢 6 倍，这就是滞回——风扇转起来会把 CPU 吹凉，吹凉了曲线又要求降速，没有阻尼就会来回振荡。实测阶跃升温约 26 秒到满速，阶跃降温约 20 秒回到最低。

## 3. 自动温控（开环，查曲线）

用平滑后的平均温度做**分段线性插值**，得到目标转速占 `[min, max]` 的比例。曲线在整个定义域上连续（低于首点取首点、高于末点取末点、中间线性过渡），不存在硬跳档。

Apple 芯片和 Intel 温度量级完全不同，所以两套曲线分开校准，运行时按 `hw.optional.arm64` 自动选择。

Apple 芯片曲线（横轴＝平滑后的核心平均温度）：

| 档位 | 控制点（温度°C → 比例） |
|---|---|
| 静音 | 60→0.00, 68→0.20, 75→0.45, 82→0.75, 90→1.00 |
| 均衡 | 55→0.00, 62→0.25, 68→0.50, 74→0.75, 80→1.00 |
| 强力降温 | 52→0.00, 58→0.30, 64→0.60, 70→0.85, 76→1.00 |

取值逻辑（对照第 1 节的实测表）：

- **起点**都落在真空闲 52°C 附近或之上，保证空闲时风扇不无谓提速。
- **满速点**落在 76–90°C。因为满载满速的物理下限是 65°C，曲线在 65°C 给出的比例（强力降温 ≈0.64、均衡 ≈0.38）会让系统收敛在**略高于 65°C** 的位置——这是合理的负反馈平衡点，而不是把风扇钉死在满速。

## 4. 目标温度（闭环，PI 控制器）

开环曲线的固有局限：它只保证"温度高就转得快"，**不保证温度最终停在哪里**。如果需求是"把 CPU 稳定在 75°C"，必须闭环。

`.target` 模式用一个带死区和抗积分饱和的 PI 控制器，直接把温度作为被控量：

```
误差 error  = 平滑平均温度 − 目标温度
输出 output = Kp · error + Ki · ∫error dt      （夹在 0~1）
```

| 参数 | 取值 | 整定依据 |
|---|---|---|
| `Kp` | 0.035 /°C | 实测风扇全量程控温能力约 22°C，倒数 1/22 ≈ 0.045 是"一步到位"的增益；取 0.035 留裕度不过冲。直观含义：每高出目标 1°C，转速 +3.5% 量程（≈137 RPM） |
| `Ki` | 0.0015 /°C/s | `Kp/Ki ≈ 23s` 的积分时间常数，比本机热时间尺度（EMA 8s + 阶跃 30s 收敛）更慢，避免与平滑环节共振 |
| 死区 | 4°C（默认，可 1–10） | 温度落在 `[目标−4, 目标]` 内就**冻结积分、保持输出** |
| 不可达判定 | 连续 60s | 满速且仍高于目标超过 60s → 界面弹橙色警示 |

四个关键设计，缺一个都会出问题：

**死区。** 风扇吹凉 CPU → 温度降 → 降速 → 温度升，这是个负反馈环。没有死区风扇会在目标线附近持续抽动。离线仿真对比：死区 4°C 时稳态转速累计行程 **36 RPM/分钟**；关掉死区则是 **781 RPM/分钟**（22 倍）。

**抗积分饱和（conditional integration）。** 输出被夹到 0 或 1 时停止累积。不做这个，用户设一个不可达的目标（比如 50°C）就会让积分项无限增长，风扇被永久钉在 4900 RPM，之后温度掉下来也要几分钟才降速——完全违背这个模式的意义。仿真验证：积分项封顶在 557（理论上界 `1/Ki` = 667），而同条件下不做抗饱和的对照组会涨到相当于 266% 输出。

**不可达检测。** 满速仍压不住就明确告诉用户"这个目标对本机不可达"，而不是默默一直吹。

**模式切换重置。** 切进 `.target` 时积分归零、输出从风扇当前实际比例接续，不带上一次的历史状态。

## 5. 高温保护

独立于上面四步，优先级最高。

平滑后的**单核峰值**温度 ≥ 阈值（默认 100°C）就强制满速、无视当前模式，且**跳过限速立即拉满**；要降到 `阈值 − 5°C` 才解除。

触发和解除用不同阈值（滞回带宽 5°C），避免在阈值附近反复横跳。

> 早期版本用的是**瞬时单核**温度加 95°C 阈值，那个组合在 Apple 芯片上会频繁误触发——单核瞬时值噪声极大，一秒内跳 20°C 是常态。现在改用平滑峰值 + 100°C + 滞回。
