# 技术原理：SMC 与平台差异

← 返回 [README](../README.md)

本文说明这个工具靠什么控制风扇、为什么不同机型走不同路径，以及代码结构。

---

## 1. 一个现实限制

苹果**没有公开的风扇控制 API**。所有控速都靠读写 SMC（System Management Controller，系统管理控制器）的私有接口。

在 Apple 芯片上，macOS 的 `thermalmonitord` 默认把风扇锁在"系统模式"，会**拦截或抢回**手动写入。本工程的应对是三段式：

1. 先尝试直接写风扇模式键；
2. 不行就走逆向出来的 `Ftst` 诊断解锁序列再重试；
3. 由常驻守护进程每 0.7 秒重写一次，持续"压住"控制权。

各代芯片表现不同（基于公开逆向资料与本机实测）：

| 芯片 | 情况 |
|---|---|
| M1 | 通常可直接进入手动模式，成功率高 |
| M2 / M3 | 未充分验证，按 M4 路径尝试 |
| M4 | 部分机型需要 `Ftst` 解锁。但**实测 Mac mini（Mac16,10）的 SMC 里根本没有 `Ftst` 键**，只能走直接写模式键这一条路；系统若拒绝就没有后手 |
| M5 | 模式键变成小写 `F0md` 且无 `Ftst`，可直接写——本工程自动探测大小写 |

个别新机型可能"写了没反应"（系统强行覆盖）。这种情况下 App 仍可正常**监控**，面板会明确显示控速未生效及原因——这是系统层限制，不是代码缺陷。

## 2. Intel Mac 走的是另一套机制

Intel Mac 分两代，本工程都已实现，运行期按机型自动选择：

| 机型 | 控制通道 | 说明 |
|---|---|---|
| Apple 芯片（M 系列） | `F{i}Md = 1` + 必要时 `Ftst` 解锁 | 已在 M4 Mac mini 实测通过 |
| **T2 Intel（2018 及以后）** | `F{i}Md = 1` | 和 Apple 芯片同一条路径；这类机型的 `FS!` 键缺失或被忽略 |
| **T2 之前的 Intel（2017 及以前）** | `FS! ` 位掩码 | 没有 `F{i}Md` 键，只能写 `FS!`（位 N = 风扇 N 强制手动），再写 `F{i}Tg` |

几个实现要点：

- **`FS!` 键名只有 3 个可见字符，第 4 位是空格。** `SMCConnection.stringToKey` 在不足 4 字符时会自动补 `0x20`，所以代码里写 `"FS!"` 即可。
- **目标转速的数据类型因机型而异**：Apple 芯片和 T2 机型的 `F{i}Tg` 是 4 字节浮点（`flt`），老 Intel 是 2 字节定点（`fpe2`，值 ×4 大端）。本工程**不硬编码类型**，而是先用 `readKeyInfo` 取该键在固件里的真实类型再编码，所以两者自动都对。
- **归还系统控制时，除了把模式键写回 0，还会清掉 `FS!` 里对应的强制位。** 漏清这一步会把风扇永久留在强制模式，比控速失败更危险。
- 平台判断用 `sysctlbyname("hw.optional.arm64")`，查的是**硬件**而非进程架构，所以在 Rosetta 下运行也能得到正确结果。

> ⚠️ **Intel 的温控曲线未经实机验证。** 曲线控制点是在 M4 Mac mini 上实测校准的，Intel 的温度量级完全不同（`TC0P` / `TC0D` 空闲 40–50°C、满载 90°C+），`intelPoints` 是按公开资料给的经验值。
>
> 如果你有 Intel Mac，欢迎通过[机型适配报告](https://github.com/nzleo/LeoMacFanControl/issues/new?template=compat-report.yml)回报实测数据，这对校准曲线非常有价值。

## 3. 架构

```
菜单栏 App (LeoFanControl，普通权限)
  │   · 直接读 SMC 显示温度/转速（只读，无需 root）
  │   · 通过本机 Unix socket 把"模式/曲线/目标温度/转速"下发给守护进程
  ▼
root 守护进程 (fanhelperd，由 LaunchDaemon 以 root 启动)
  │   · 持有 SMC 连接，跑控速循环（约每 0.7s 重写一次，压住系统抢回）
  │   · 温度平滑、曲线插值 / PI 闭环、升降速限速、高温保护都在这里
  │   · Ftst 解锁 + 写风扇模式/目标转速
  ▼
AppleSMC 内核驱动 → SMC 固件 → 风扇
```

为什么要拆成两个进程：控速必须 root，但菜单栏 GUI 不该以 root 运行。把 root 权限收敛到一个只做 SMC 读写的小程序里，攻击面最小，也最容易审计。

### 代码结构

| 路径 | 作用 |
|---|---|
| `Sources/FanControlCore/` | 共享核心：SMC 通信、数据编解码、风扇控制、曲线、IPC 协议 |
| `Sources/LeoFanControl/` | 菜单栏 GUI（SwiftUI） |
| `Sources/fanhelperd/` | root 守护进程 |
| `Scripts/` | 构建、打包、安装脚本 |

关键文件：

- `SMCConnection.swift` —— 与 `AppleSMC` 内核驱动通信的底层封装（80 字节参数结构、命令码、FourCC 编解码）
- `SMCReader.swift` —— 高层只读接口：风扇快照、温度传感器发现、`Ftst` / `FS!` 探测
- `FanController.swift` —— 写入路径：进入手动模式、设目标转速、归还系统
- `FanCurveEngine.swift` —— 温度平滑、曲线插值、PI 闭环、限速、高温保护
- `Daemon.swift` —— 控速循环与 IPC 处理，含配置范围夹取

## 4. 温度传感器的选择

Apple 芯片和 Intel 的 CPU 温度传感器命名完全不同，必须分开处理：

- **Apple 芯片**：P 核 `Tp..` / E 核 `Te..` 簇传感器（本机实测有 55 个）
- **Intel**：`TC..` 系列

早期版本对两者一律放行，结果在 Apple 芯片上把 `TCMb` / `TCMz` 之类的**非 CPU** 键也混进了平均值，拉高读数。现在的逻辑是：只要发现了 Apple 的核心簇传感器，就完全忽略 `TC..` 键。

传感器发现时还会过滤掉解析不出合理温度的键（要求 5°C < 读数 < 120°C），避免同名但语义不同的键污染结果。

## 5. 技术致谢

SMC 协议常量、`Ftst` 解锁机制、`FS!` 强制模式位掩码、各代芯片差异等原理，参考了公开的逆向研究与文档（Asahi Linux SMC 文档、社区 SMC 键表、smcFanControl 等开源项目的研究记录）。

本工程的全部代码为自行实现，未直接使用第三方二进制或库。
