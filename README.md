# Leo 风扇控制（LeoMacFanControl）

一个 macOS 原生菜单栏 App，用来监控 CPU 温度 / 风扇转速，并在 Mac mini / MacBook 上**按温度曲线自动升速降温**、**把温度闭环稳定在指定目标值**，或**手动固定转速**。

> 适用：Apple 芯片（M1–M5）与 Intel Mac。专为"Mac mini 高负载时风扇不主动升速、机身过热"这类场景设计。

---

## 1. 为什么要自己写（隐私说明）

控速必须给一个进程 **root 权限**。市面上的第三方风扇软件你无法逐行确认它拿到 root 后还做了什么。本工程：

- **全部源码自己写、可逐行审计**，只用 Apple 自带框架（IOKit / Foundation / SwiftUI / ServiceManagement / AppKit / Combine / Darwin）。
- **没有任何网络代码**（不 import 任何网络库，不发任何请求）。你可以全局搜索 `URLSession` / `import Network` / `AF_INET` / `http`，结果为空。全工程只有 `AF_UNIX`（本机进程间通信）这一处 socket。
- 不启动任何子进程、不做动态加载（无 `Process` / `posix_spawn` / `dlopen`）。
- root 守护进程只做一件事：读写 SMC 风扇键。它通过**本机 Unix socket** 接受固定的四条指令（设配置 / 取状态 / 探活 / 停止），不监听任何网络端口。
  - socket 权限为 `root:admin 0660`：只有本机管理员用户（本来就能 `sudo` 的那些人）能下发控速指令，其他用户和沙盒进程都被内核直接拒绝。
  - 之所以不用 `0600`：菜单栏 App 以普通用户身份运行，`0600` 会让它永远连不上守护进程、只能显示"仅监控"。
  - 守护进程对收到的配置一律做范围夹取（转速 0–100%、保护温度 85–110℃、目标温度 65–90℃、死区 1–10℃，`NaN` 一律退回默认值），不信任任何外部输入。

---

## 2. 先了解一个现实限制（很重要）

苹果**没有公开的风扇控制 API**。所有控速都靠读写 SMC（系统管理控制器）的私有接口，且在 Apple 芯片上：

- macOS 的 `thermalmonitord` 守护进程默认把风扇锁在"系统模式"，会**拦截/抢回**手动写入。本工程用两段式策略应对：先尝试直接写模式；不行就走逆向出来的 `Ftst` 诊断解锁序列；并由常驻守护进程持续"压住"控制权。
- **各代芯片表现不同**（基于公开逆向资料）：
  - **M1**：通常可直接进入手动模式，成功率高。
  - **M2 / M3**：未充分验证，按 M4 路径尝试。
  - **M4**：部分机型需要 `Ftst` 解锁，本工程已实现。但**实测 Mac mini（Mac16,10, M4）的 SMC 里根本没有 `Ftst` 键**，只能走"直接写模式键"这一条路；如果系统拒绝，就没有别的后手了。
  - **M5**：模式键变成小写 `F0md`、且无 `Ftst`，可直接写——本工程已自动探测大小写。
- 个别新机型可能"写了没反应"（系统强行覆盖）。如果遇到，App 仍可正常**监控**，面板上会明确显示"控速未生效"及原因——这是系统层限制，不是代码 bug。
- ⚠️ **风险**：把风扇设得过低可能导致过热。本工程的自动曲线只会"按需升速"，目标温度模式的可设范围下限也卡在物理可达的 65°C，手动转速则被夹在硬件 `min~max` 区间内；三种模式之上还有**高温强制满速保护**（默认 ≥100°C，可在面板里 85–110°C 之间调整），优先级高于一切模式。但仍请留意温度，自担风险。

## 3. 架构

```
菜单栏 App (LeoFanControl，普通权限)
  │   · 直接读 SMC 显示温度/转速（只读，无需 root）
  │   · 通过本机 Unix socket 把"模式/曲线/目标温度/转速"下发给守护进程
  ▼
root 守护进程 (fanhelperd，由 LaunchDaemon 以 root 启动)
  │   · 持有 SMC 连接，跑控速循环（约每 0.7s 重写一次，压住系统抢回）
  │   · 温度平滑、曲线插值 / PI 闭环、升降速限速、高温保护都在这里
  │   · Ftst 解锁 + 写风扇模式/目标转速
  ▼
AppleSMC 内核驱动 → SMC 固件 → 风扇
```

- `Sources/FanControlCore/`：共享核心（SMC 通信、数据解码、风扇控制、曲线、IPC 协议）。
- `Sources/LeoFanControl/`：菜单栏 GUI。
- `Sources/fanhelperd/`：root 守护进程。
- `Scripts/`：构建与安装脚本。

## 4. 本机实测数据（所有校准的依据）

下面这张表是 **M4 Mac mini（Mac16,10，10 核，风扇 1000–4900 RPM）** 的实测结果，
本工程里所有曲线控制点和 PI 参数都是按它整定的。温度全部是**平滑后的核心平均温度**
（括号里是平滑后的单核峰值）：

| 场景 | 1000 RPM（最低） | 4900 RPM（满速） |
|---|---|---|
| **真空闲** | **~52°C**（峰值 ~62°C），稳定 | **~48°C**（峰值 ~60°C），稳定 |
| **10 线程满载** | **>87°C 且持续上升**（峰值 >103°C）<br>90 秒未收敛，被迫中止测试 | **~65°C**（峰值 ~79°C）<br>30 秒内收敛，非常稳定 |

三条结论：

1. **风扇在负载下的控温能力约 22°C（平均）/ 24°C（峰值）**——非常大，值得用。
2. **macOS 默认策略在满载时把风扇死守 1000 RPM**，压不住，温度会一路爬到 SoC 自己降频。
   （随手一测：写这段文档时正在编译，`smoothedTempC = 77.7°C`、峰值 96°C，系统模式下风扇仍然是 1000 RPM。）
3. **真空闲是 52°C，不是 71°C。** 早期版本的曲线是按 71°C 的空闲基线校准的，
   那个 71°C 其实是"边编译边测"的污染数据。按 71°C 起步的曲线在日常使用时长期输出 0
   （等于没装这个软件），等温度冲过 87°C 又突然满速，体验是"要么不动要么狂转"。
   现在的控制点已按上表重新校准。

> Intel 曲线**未经实机验证**，仍按 Intel Mac 的传统温度量级（空闲 40–50°C、满载 90°C+）给出，
> 没有做过上面这种四象限实测。Intel 用户请自行观察后调整。

## 5. 温控算法（怎么决定转速）

每 0.7 秒一个控制周期，依次做四件事（实现见 `Sources/FanControlCore/FanCurveEngine.swift`）：

**① 取温度。** 枚举 SMC 全部键，挑出 CPU 核心簇传感器（Apple 芯片本机有 55 个 `Tp..` / `Te..`，Intel 是 `TC..`），
算出两个量：**核心平均温度**（喂给曲线和 PI）和**单核峰值温度**（喂给高温保护）。

**② 低通平滑。** 对两个量各做一阶 EMA，时间常数 8 秒。
这一步不能省：Apple 芯片的单核传感器噪声极大，实测同一秒内不同核心能差 20°C 以上，
单核瞬时值在有负载时一秒内就能从 74°C 跳到 97°C。直接拿瞬时值去查曲线，风扇会一直抖。
**所以曲线和 PI 的输入一律是平滑后的平均值，绝不是最高值。**

**③ 决定目标比例。** 这一步按模式分成开环和闭环两条路：

### ③-a 自动温控（开环，查曲线）

用平滑后的平均温度做**分段线性插值**，得到目标转速占 `[min, max]` 的比例。
曲线在整个定义域上连续（低于首点取首点、高于末点取末点、中间线性过渡），不存在硬跳档。
Apple 芯片和 Intel 的温度量级完全不同，所以两套曲线分开校准，运行时按 `hw.optional.arm64` 自动选择。

Apple 芯片曲线（横轴＝平滑后的核心平均温度）：

| 档位 | 控制点（温度°C → 比例） |
|---|---|
| 静音 | 60→0.00, 68→0.20, 75→0.45, 82→0.75, 90→1.00 |
| 均衡 | 55→0.00, 62→0.25, 68→0.50, 74→0.75, 80→1.00 |
| 强力降温 | 52→0.00, 58→0.30, 64→0.60, 70→0.85, 76→1.00 |

取值逻辑（对照第 4 节的实测表）：

- **起点**都落在真空闲 52°C 附近或之上，保证空闲时风扇不无谓提速。
- **满速点**落在 76~90°C。因为满载满速的物理下限是 65°C，曲线在 65°C 给出的比例
  （强力降温 ≈0.64、均衡 ≈0.38）会让系统收敛在**略高于 65°C** 的位置——
  这是合理的负反馈平衡点，而不是把风扇钉死在满速。

### ③-b 目标温度（闭环，PI 控制器）

开环曲线的固有局限：它只保证"温度高就转得快"，**不保证温度最终停在哪里**。
如果需求是"把 CPU 稳定在 75°C"，必须闭环。`.target` 模式用一个带死区和抗积分饱和的
PI 控制器，直接把温度作为被控量：

```
误差 error  = 平滑平均温度 − 目标温度
输出 output = Kp · error + Ki · ∫error dt      （夹在 0~1）
```

| 参数 | 取值 | 整定依据 |
|---|---|---|
| `Kp` | 0.035 /°C | 实测风扇全量程的控温能力约 22°C，倒数 1/22 ≈ 0.045 是"一步到位"的增益；取 0.035 留裕度不过冲。直观含义：每高出目标 1°C，转速 +3.5% 量程（≈137 RPM） |
| `Ki` | 0.0015 /°C/s | `Kp/Ki ≈ 23s` 的积分时间常数，比本机热时间尺度（EMA 8s + 阶跃 30s 收敛）更慢，避免与平滑环节共振 |
| 死区 | 4°C（默认，可 1–10） | 温度落在 `[目标−4, 目标]` 内就**冻结积分、保持输出** |
| 不可达判定 | 连续 60s | 满速且仍高于目标超过 60s → 界面弹橙色警示 |

四个关键设计，缺一个都会出问题：

- **死区**：风扇吹凉 CPU → 温度降 → 降速 → 温度升，这是个负反馈环。没有死区风扇会在目标线附近
  持续抽动。离线仿真对比：死区 4°C 时稳态转速累计行程 **36 RPM/分钟**；关掉死区则是 **781 RPM/分钟**（22 倍）。
- **抗积分饱和（conditional integration）**：输出被夹到 0 或 1 时，停止累积会让饱和更严重的那个方向的误差。
  不做这个，用户设一个不可达的目标（比如 50°C）就会让积分项无限增长，风扇被永久钉在 4900 RPM，
  之后温度掉下来也要几分钟才降速——完全违背这个模式的意义。仿真验证：积分项封顶在 557（理论上界 `1/Ki` = 667），
  而同条件下不做抗饱和的对照组会涨到相当于 266% 输出。
- **不可达检测**：满速仍压不住就明确告诉用户"这个目标对本机不可达"，而不是默默一直吹。
- **模式切换重置**：切进 `.target` 时积分归零、输出从风扇当前实际比例接续，不带上一次的历史状态。

**④ 升降速限速（滞回）。** 转速不会直接跳到目标值，而是限速逼近：
**升速最快 30%/秒，降速最快 5%/秒**。降速刻意比升速慢 6 倍，这就是滞回——
风扇转起来会把 CPU 吹凉，吹凉了曲线又要求降速，没有阻尼就会来回振荡。
实测阶跃升温约 26 秒到满速，阶跃降温约 20 秒回到最低。

**高温保护**独立于上面四步，优先级最高：平滑后的**单核峰值**温度 ≥ 阈值（默认 100°C）就强制满速、
无视当前模式，且**跳过限速立即拉满**；要降到 `阈值 − 5°C` 才解除。触发和解除用不同阈值（滞回带宽 5°C），
避免在阈值附近反复横跳。

## 6. 编译与安装（按顺序）

前置：macOS 13+、已装 Xcode（含命令行工具）。

### 第 1 步：编译并打包 GUI

在项目根目录（普通用户，不用 sudo）：

```bash
./Scripts/build-app.sh
```

生成 `LeoFanControl.app`。可把它拖进 `/Applications`。双击即可运行（菜单栏出现风扇图标 + 温度）。
此时已经能**监控**温度和转速。

> 也可以直接用 Xcode 打开：`File ▸ Open` 选中项目根目录里的 `Package.swift`，选 `LeoFanControl` scheme 运行。

### 第 2 步：安装 root 守护进程（控速才需要）

```bash
# 1) 先编译守护进程（普通用户）
swift build -c release --product fanhelperd

# 2) 再以 root 安装并启动（会注册为开机自启的 LaunchDaemon）
sudo ./Scripts/install.sh
```

装好后，App 面板右上角会从"仅监控"变成"守护进程运行中"，这时"自动温控 / 目标温度 / 手动固定"才会真正生效。

> **从 1.1 升级上来的话，守护进程必须一起重装。** 新增的"目标温度"模式在旧版守护进程的
> 枚举里不存在，旧二进制会拒绝这条配置（面板显示控速未生效）。配置文件本身是向后兼容的：
> 旧 `config.json` 缺少新字段时会自动退回默认值（目标 75°C / 死区 4°C），不会丢设置。

## 7. 使用

点击菜单栏图标弹出面板：

- **控制模式**（四个）：
  - `系统自动`：交还给 macOS（最安全，默认）。
  - `自动温控`：按曲线随温度自动升降速（开环）。
  - `目标温度`：PI 闭环，把核心平均温度**稳定在指定值附近**。
  - `手动固定`：用滑块设定一个固定转速百分比。
- **温控档位**（自动温控下）：`静音 / 均衡 / 强力降温`。越强越早提速、越压温度。
- **目标温度**（目标温度模式下）：65–90°C 可调，默认 75°C。
  - 下限 65°C 是**物理下限**：本机实测满载 + 满速也只能压到 65°C，设得比这更低的目标根本不可达。
  - 温度**低于目标 4°C**（死区）才会开始降速，所以实际稳态落在 `[目标−4, 目标]` 区间里。
  - 如果满速仍压不到目标并持续 60 秒，面板会弹出橙色警示提示你调高目标值。
- **手动转速**（手动固定下）：0–100%，对应风扇最低～最高转速。
- **高温保护**：85–110°C 可调，默认 100°C。任何模式下超过它都强制满速。
- **开机自动启动**：登录时自动拉起 App（`SMAppService`）。
  - 守护进程已经是开机自启（LaunchDaemon），所以即使没开 App，上次的控速配置也会在重启后自动恢复。

面板顶部同时显示**核心平均温度**（大字，也是曲线和 PI 的输入）和**单核峰值温度**（小字，高温保护的输入）。
两者差 10–15°C 是 Apple 芯片的正常现象，不是读数错误（实测 52/62、65/79）。

### 选哪个模式？

- **想要"温度别超过某个值"** → `目标温度`。这是最直接对应需求的模式：设 75°C，
  风扇就会自己找到那个刚好压住 75°C 的转速（本机满载下约 2700 RPM），温度降下来转速也会跟着降下来。
- **想要"安静优先、热了再说"** → `自动温控 + 静音`。
- **跑长时间 AI / 编译任务、希望尽量压温度** → `自动温控 + 强力降温`，或 `目标温度` 设 70°C。
- **只想让它别吵** → `手动固定` 一个你能接受的百分比。

## 8. 卸载

```bash
sudo ./Scripts/uninstall.sh
```

会停止并移除守护进程，并把风扇**交还给 macOS 自动控制**。GUI 直接删除 `LeoFanControl.app` 即可；如开了自启，先在面板里关掉开关。

## 9. 故障排查

- **面板一直显示"仅监控"**：守护进程没装或没起来。检查：`sudo launchctl print system/com.leo.fancontrol.helper`，看日志：`sudo tail -f /Library/Logs/LeoFanControl/fanhelperd.log`。
- **选了"目标温度"但控速未生效**：守护进程还是 1.1 版。重新 `swift build -c release --product fanhelperd` 并 `sudo ./Scripts/install.sh`。
- **目标温度模式弹橙色"该目标对本机不可达"**：设的目标低于本机物理下限。满载时本机满速也只能到 65°C，
  把目标调高即可（这条警示要满速且持续高于目标 60 秒才出现，不会误报）。
- **目标温度模式下温度稳定在比目标低 2–4°C 的位置**：这是死区的正常表现，不是偏差。
  死区让风扇在 `[目标−4, 目标]` 区间里不动作，避免来回抽速。
- **温度显示 `--`**：读不到 CPU 传感器（极少见）。该机型传感器键可能特殊，可在 issue 里反馈具体型号。
- **改了转速没反应**：面板底部会显示具体原因。若提示"系统拒绝进入手动模式"，说明命中了前述系统限制，
  守护进程会按 2/4/8…60 秒退避重试，不会把 CPU 占满。
- **面板显示"仅监控"但守护进程确实在跑**：确认你的账号在 `admin` 组里（`id -Gn | grep admin`）。
  socket 是 `root:admin 0660`，非管理员账号连不上。
- **`swift build` 报缺少命令行工具**：先 `xcode-select --install`。
